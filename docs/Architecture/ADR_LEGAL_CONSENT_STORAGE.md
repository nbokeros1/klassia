# ADR — Legal Consent Storage Model
**ID:** ADR-LEGAL-001  
**Date:** 2026-08-21  
**Status:** ACCEPTED  
**Replaces:** Migration 046 (mutable fields on utilisateurs)

---

## Context

ScorgIA V1.0 shipped a legal checkbox at signup (commit `392ffee`) that rejects signups with `legalAccepted !== true`. Consent is validated at the API layer but not durably stored anywhere.

We now need to decide HOW to store consent evidence before the product grows beyond controlled beta.

---

## Decision drivers

1. **Auditability** — we must be able to prove WHO accepted WHAT version WHEN.
2. **Independent versioning** — Terms and Privacy update on separate release cycles.
3. **Immutability** — historical acceptance must survive future version bumps.
4. **Server authority** — timestamps and user identity must be server-generated, never client-controlled.
5. **Privacy** — minimum necessary data; no unnecessary fields; deletion removes records.
6. **Simplicity** — ScorgIA is in controlled beta; don't build enterprise contract management.

---

## Evaluated models

### Model A — Mutable fields on `utilisateurs`

```sql
ALTER TABLE utilisateurs
  ADD COLUMN terms_version      TEXT,
  ADD COLUMN privacy_version    TEXT,
  ADD COLUMN legal_accepted_at  TIMESTAMPTZ;
```

**Pros:** Simple, no new table, no join.  
**Cons:**
- Overwrites historical acceptance on re-consent → no audit trail
- Single timestamp for two independently versioned documents
- No `acceptance_context` (can't tell if consent was at signup vs. legal update)
- No database guarantee on timestamp authority
- Consent fields live alongside mutable profile data, fragile to access-broadening
- Can't answer "When did user X accept Privacy v1.0?"

**Verdict: REJECTED.** Mutable fields cannot satisfy audit requirements.

### Model B — Dedicated append-only `legal_consents` table

```sql
CREATE TABLE legal_consents (
  id                 UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id            UUID        NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  utilisateur_id     UUID        REFERENCES utilisateurs(id) ON DELETE SET NULL,
  terms_version      TEXT        NOT NULL,
  privacy_version    TEXT        NOT NULL,
  acceptance_context TEXT        NOT NULL DEFAULT 'beta_signup',
  accepted_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  created_at         TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**Pros:**
- Append-only: historical acceptance is never overwritten
- Per-event timestamps, unambiguous attribution
- Independent Terms and Privacy version columns
- Server-authoritative `accepted_at DEFAULT now()` (not client-settable)
- `acceptance_context` records the flow (beta_signup, legal_update, etc.)
- Dedup index prevents double-click duplicates while allowing future re-consent
- RLS segregated from profile data
- Deletion cascades cleanly via `auth.users(id) ON DELETE CASCADE`

**Cons:**
- Requires one JOIN to get current consent status
- New table (migration complexity)

**Verdict: ACCEPTED.** Audit requirements mandate event-sourced design.

---

## Decision

**Use Model B: dedicated append-only `legal_consents` table.**

**Rationale:** Legal acceptance is an EVENT, not a property. Events must be recorded in an append-only store. This is consistent with `activity_events` and `audit_trail` already present in the ScorgIA architecture.

---

## Consent record — field rationale

| Field | Justification |
|-------|--------------|
| `id` | UUID PK — standard row identity |
| `user_id` | `auth.users.id` — canonical identity; FK with cascade delete |
| `utilisateur_id` | `utilisateurs.id` — convenience join; nullable (SET NULL on cascade) |
| `terms_version` | NOT NULL — which Terms version was accepted |
| `privacy_version` | NOT NULL — which Privacy version was accepted; independent lifecycle |
| `acceptance_context` | NOT NULL — which flow triggered this acceptance |
| `accepted_at` | NOT NULL DEFAULT now() — server-generated by PostgreSQL |
| `created_at` | NOT NULL DEFAULT now() — technical row creation timestamp |

**Fields NOT collected:**
- IP address — not necessary for V1.1, adds privacy surface
- Device/browser fingerprint — not necessary, invasive
- User agent — not necessary
- Geographic data — not necessary
- Hash of document content — useful future extension, not required for V1.1

---

## Identity resolution at signup time

The signup flow creates an `auth.users` record before `utilisateurs` is upserted. The consent event must reference `auth.users.id` as the primary identity anchor (not `utilisateurs.id` which may not exist yet at the time of writing the event).

In practice: the beta-signup API route:
1. Creates auth user → gets `data.user.id`
2. Waits 1200ms (trigger delay)
3. Upserts `utilisateurs` → gets `profil.id`
4. Writes consent event with both `user_id = data.user.id` and `utilisateur_id = profil.id`

If step 4 fails: log `[LEGAL_CONSENT_WRITE_FAILED]`, do not fail the signup (account exists), flag for re-consent on next login via the `getLegalConsentStatus()` helper.

---

## Append-only enforcement strategy

- No `UPDATE` or `DELETE` policy granted to `authenticated` role
- `INSERT` only via service role (bypasses RLS), called from server API routes
- Dedup unique index: `(user_id, terms_version, privacy_version, acceptance_context)` prevents exact duplicate events
- Uniqueness is partial — future re-consents for new versions (e.g., terms v1.1) generate new rows without conflict

---

## Data deletion and privacy tension

**Tension:** Audit evidence vs. right to erasure.

**Resolution for V1.1:** `ON DELETE CASCADE` from `auth.users.id`. When a user deletes their account, all consent records are deleted. This prioritizes privacy (right to erasure). The implication: after account deletion, we cannot prove they ever accepted; this is acceptable for the current user base size and risk profile.

**Future consideration:** For larger commercial operation with regulatory exposure, a retention strategy (e.g., retain hashed or anonymized consent event for N years after deletion) could be designed. This is out of scope for V1.1.

---

## Re-consent engine design

Version comparison is exact-equality, not semantic:

```
termsCurrent     = (acceptedTermsVersion === LEGAL_VERSIONS.terms)
privacyCurrent   = (acceptedPrivacyVersion === LEGAL_VERSIONS.privacy)
requiresAction   = !termsCurrent || !privacyCurrent || !hasConsent
```

This means bumping `LEGAL_VERSIONS.terms` to `'1.1'` in `constants.ts` is the trigger for requiring re-consent. Any change to that value should be deliberate and reviewed.

**Required acceptance version vs. display version:** V1.1 uses the same value for both. Future versions may introduce a `LEGAL_REQUIRED_VERSIONS` constant distinct from `LEGAL_VERSIONS` (display) if minor errata updates don't require re-acceptance.

---

## Existing beta users

- Pre-`392ffee` users: No consent evidence. Category B.
- Post-`392ffee`, pre-V1.1: Checkbox was required, no DB record. Category B.
- Post-V1.1-migration: Category A.

No retroactive fabrication. Category B users face a re-consent prompt on next login once the re-consent middleware is activated.

---

## Consequences

- Migration `046_legal_consents_V11_FINAL_PROPOSED.sql` replaces `046_legal_consents_PROPOSED.sql`
- `getLegalConsentStatus()` is the single deterministic interface for checking consent state
- `beta-signup` route gains a consent event write after utilisateurs upsert
- Re-consent middleware (future) gates dashboard access for Category B users after activation
